# Global Vault — Shared Brain for AI Context

A `.ai/global/` directory inside the project repo acts as a shared brain for any AI agent. Travels with the project via git, requires no external config.

## When to Use

- Multi-machine teams where AI agents (Claude, Trae) need shared context
- AI agents must follow team standards without per-machine setup
- Discovered skills/patterns should propagate automatically
- Token-efficient context (structured YAML, not prose)

## Architecture

```
project/
├── .ai/
│   ├── MASTERPROMPT.md          # Generated by ai project init
│   ├── memory.yaml              # Local memory
│   └── global/                  # ← SHARED BRAIN
│       ├── rules/               # Team rules
│       ├── skills/              # Discovered tools
│       ├── patterns/            # Architecture patterns
│       ├── projects/            # Team projects index
│       └── index.yaml           # Search index
└── src/
```

## Architecture: Two-Layer Vault

The vault has **two layers** that merge at read time:

```
.ai/global/
├── shared/                    ← GLOBAL (from AIEP repo, applies to ALL projects)
│   ├── rules/                 ← Team-wide coding standards, git workflow
│   ├── skills/                ← Tools discovered across all projects
│   └── patterns/              ← Architecture patterns (clean-architecture, tdd)
├── rules/                     ← Project-specific rules (override shared)
├── skills/                    ← Project-specific skills
├── patterns/                  ← Project-specific patterns
├── projects/                  ← Project metadata
├── vault.yaml                 ← Vault state
└── index.yaml                 ← Search index
```

**Merge semantics**: `get_rules()` returns shared rules first, then project rules override. Same for skills/patterns. Prefix `shared/` distinguishes shared entries in the merged dict.

**Write semantics**: `add_rule()` writes to project-specific. `add_shared_rule()` writes to shared (used when syncing from AIEP repo).

## MASTERPROMPT Protocol for External AIs

The MASTERPROMPT.md is the **primary context document** for external AIs. It must include:

1. **Project identity** — name, type, language, framework, dependencies, entry points
2. **Global team rules** — from vault shared layer (coding standards, git workflow)
3. **Global skills/patterns** — from vault shared layer
4. **Security requirements** — what all projects must follow
5. **Protocol for external AI**:
   - Before: read MASTERPROMPT, check memory, run `ai sync`
   - During: follow rules, use skills/patterns
   - After: update memory, run `ai sync`, create PR (not push to main)
6. **Available commands** — `ai sync`, `ai context`, `ai status`, `ai memory`
7. **Next steps** — roadmap with pending/in-progress/done tasks
8. **Persistent memory** — history of decisions and discoveries

**Key instruction**: "After each significant change, run `ai sync` to synchronize with the global repo."

## Install.sh Update Mode

When AIEP is already installed, `install.sh` should **update** not reinstall:

```bash
if is_aiep_installed && [ -f "${CONFIG_DIR}/providers.yaml" ]; then
    # Pull latest code
    git pull --rebase
    # Rebuild venv (not delete config)
    rm -rf "${VENV_DIR}"
    uv venv "${VENV_DIR}" --python 3.12 --clear
    pip install -e "${repo_root}"
    # Ensure platform_repo_root is set
    # Skip bundle extraction (config exists)
    # Exit successfully
fi
```

**Critical**: Don't ask for bundle passphrase if config already exists. Don't overwrite existing credentials.

**Sync flow per `ai` command**:
1. **Before command**: `_sync_project_vault_pull()` — copies `projects/<name>/` from AIEP repo to local `.ai/global/`
2. **Command executes**: Normal operation
3. **After command**: `_sync_project_vault_push()` — copies local `.ai/global/` to `projects/<name>/` in AIEP repo + auto-commit + push

## Multi-IA Bridge Architecture

AIEP must be the **central brain** for ALL installed IAs (Hermes, Claude, Codex, Aider, OpenHands). Each IA feeds context to AIEP and receives synchronized rules/patterns back.

### Bridge Components:

1. **Hermes Bridge** (`aiep.hermes_bridge.core.HermesBridge`):
   - Imports 89+ Hermes skills to AIEP vault
   - Syncs memory bidirectionally
   - Exports AIEP context for Hermes to consume
   - CLI: `python -m aiep.hermes_bridge <status|import-skills|sync-memory|export-context>`

2. **IA Bridge** (`aiep.ia_bridge.RuleSyncService`):
   - Detects installed IAs automatically
   - Propagates new rules to ALL IAs simultaneously
   - Auto-updates documentation (MASTERPROMPT.md, ROADMAP.md) with active rules
   - CLI: `python -m aiep.ia_bridge <status|add-rule|sync-all|list-rules>`

### Rule Synchronization Flow:
1. IA discovers new rule → AIEP stores in `.ai/global/rules/`
2. AIEP propagates to all IAs via their bridges
3. MASTERPROMPT.md and ROADMAP.md auto-update with `<!-- AIEP_RULES -->` marker
4. All subsequent IA sessions see the updated rules

### Automatic Rule Collection (NEW 2026-08-20)

**Critical**: AIEP must AUTOMATICALLY collect rules from ALL IA sessions, not just Hermes. When ANY IA (Claude Code, Codex, Aider) tells the user "always do X" or the user corrects an IA with "remember that Y", that rule must:

1. Be captured by the AIEP bridge for that IA
2. Be stored in `.ai/global/rules/` with metadata (source IA, timestamp, context)
3. Be propagated to ALL other IAs on next sync
4. Update MASTERPROMPT.md and ROADMAP.md automatically

**The `ai` command is the trigger**: Every time a user runs `ai <command>`, the auto-sync middleware:
- Pulls latest rules from AIEP vault
- Pushes any new local changes
- Reaches out to all IA bridges to collect new rules
- Distributes rules to all IAs

This means AIEP is always up-to-date without manual intervention.

**Key insight**: AIEP is not just a passive vault — it's an ACTIVE BRAIN that feeds context TO all IAs and collects knowledge FROM all IAs. Every IA session makes AIEP smarter, and AIEP makes every IA session smarter.

### IA Propagation Targets:
- **Hermes**: `~/.hermes/global_rules.yaml`
- **Claude**: `CLAUDE.md` in project root
- **Codex**: `.codex.md` in project root
- **Aider**: `.aider.md` in project root
- **OpenHands**: `.openhands.md` in project root

## Key Principles

1. **Platform does NOT execute tasks** — external AIs (Claude Code, Trae, etc.) do; platform prepares context
2. **No external config** — vault lives in the AIEP repo at `projects/<name>/`
3. **Git-native sync** — AIEP repo push/pull propagates context (no external services)
4. **Hermes generates templates** — `ai init` creates MASTERPROMPT.md using global context
5. **External IAs read MASTERPROMPT** — work without knowing about vault
6. **ai sync** — Hermes reads AI work, updates vault with new skills/patterns
7. **Token protection** — credentials encrypted, no daemon, command-based sync
8. **5+ machines** — same Hermes config, same token, background worker (not daemon)
9. **AIEP repo is the global brain** — `install.sh` stores `platform_repo_root` in config.yaml, all sync targets this repo
10. **Project vault isolation** — each project's `.ai/global/` syncs to `projects<name>/` in AIEP repo
11. **Multi-IA coordination** — AIEP propagates rules/context to ALL installed IAs, not just Hermes
12. **Repo separation by security** — public services (gateway) in public repos; private services (backup, OCR) in private repos

## Security Patterns

- Fernet + PBKDF2 (600k iterations) for credentials
- TOTP 2FA with ±30s clock skew
- `fcntl.flock(LOCK_EX)` for read-modify-write
- `chmod 0o600` on all state writes
- `yaml.safe_load()` only
- URLs validated against git remote helper injection
- Hermes config (.env, auth.json) encrypted during install

## Pitfalls

1. Don't build external sync services — vault lives in the AIEP repo
2. Don't assume platform executes tasks — external AIs do the work
3. Don't require manual git commands — auto-sync by default
4. Don't use daemon processes — command-based sync is lighter
5. Don't use Obsidian as global — Obsidian for humans, YAML for machines
6. Don't let external AIs generate initial templates — Hermes generates MASTERPROMPT
7. Don't hardcode `changes=0` — read actual state
8. Don't use bare `except: pass` — log exceptions
9. Don't skip chmod 600 on credential writes
10. Don't use yaml.load() — use yaml.safe_load()
11. Don't forget to copy Hermes config (.env, auth.json, platforms, skills) during install
12. Don't store Hermes config plaintext — encrypt with Fernet + PBKDF2
13. Don't hardcode `aiep-global` as external repo — global is the AIEP repo itself
14. Don't skip preflight checks — verify Python 3.12+, git, curl, sha256sum, Hermes, Docker, Ollama
15. Don't write skills to `.ai/global/skills/` of the project — use `registry_path` from config (`~/.local/share/aiep/skills/`)
16. Don't generate empty documentation templates — read vault and inject real rules/skills/patterns
17. Don't let git hang on credential prompts — set `GIT_TERMINAL_PROMPT=0` in sync operations
18. Don't assume memory is only in `.md` — `ai project init` writes `.yaml`, loader must handle both
19. Don't skip storing `platform_repo_root` in config during install — sync won't work without it
20. Don't forget to make install.sh idempotent — if already installed, update (pull + rebuild venv) instead of asking for credentials
21. Don't use qwen3.6 (36B) for `ai project init` — too large, causes connection closures. Prefer: qwen2.5-coder:1.5b > llama3.2 > gemma4:12b
22. Don't ask for bundle passphrase during update — if `config.yaml` already exists, skip credential prompts
23. **Don't create separate repos for gateway and automation** — they belong together in `nas-gateway` repo. Backup and OCR (sensitive) go in separate private repo `nas-services`.
24. **Don't forget to propagate rules to ALL IAs** — when a rule is discovered by any IA, it must be sent to all others. Use `python -m aiep.ia_bridge sync-all`.
25. **Don't skip repo cleanup after moving to independent repos** — after extracting services to their own repos, delete the directories from the main repo to avoid confusion.
26. **Don't leave node_modules in commits** — always add to `.gitignore` and remove from tracking before committing.
27. **Don't create standalone scripts when a package structure fits better** — move modules to `__init__.py` + `__main__.py` packages for `python -m` execution.
28. **Don't use npm** — user explicitly removed npm as a supported package manager. Only `pnpm`, `bun`, and `yarn` are allowed. Auto-detect from lockfiles; default to pnpm.
29. **Don't create repos when a production repo already exists** — `nas-infrastructure` is the actual production repo for NAS services at `~/proyectos/nas-infrastructure/`. It uses `core/` subdirectory for services (not top-level). Always check for existing production repos before creating new ones.
30. **Don't forget Portainer for NAS Docker management** — Synology NAS uses Portainer CE for Web UI Docker management. Deploy via `portainer/docker-compose.yml` with `/var/run/docker.sock` mount.

39. **Don't run `ai project init --force` without pinning the target directory** — the scaffolder writes `docs/`, `MASTERPROMPT.md`, `CLAUDE.md`, `.aider.md` relative to the *current working directory*. Invoking it from the AIEP repo itself (or any already-scaffolded project) **overwrites the repo's own documentation**. `--force` suppresses the guard that would otherwise stop it.

    Before running any scaffolder with `--force`:
    ```bash
    pwd                                  # confirm you are in the TARGET project
    git -C <target> status --short        # must be clean, so a bad run is revertible
    ```
    Prefer driving the analyzer/docgen against an explicit `Path` (see
    `references/scaffolder-safety.md`) over relying on cwd.

    Recovery when it does clobber tracked files — restore from git, do not rewrite by hand:
    ```bash
    git checkout -- docs/ MASTERPROMPT.md   # tracked files come back intact
    rm -f CLAUDE.md .aider.md               # newly-created untracked files: just delete
    git status --short                      # verify clean before continuing
    ```
    This only works if the repo was committed beforehand — which is why the pre-flight
    `git status` check matters more than the recovery command.
