# Music Syncer Status Server Pattern

## Session Date
2026-08-21

## Context
The music-syncer container ran a daily sync loop (`sync.sh`) that generated a `summary_report.txt`, but there was no programmatic way to check the current status — you'd have to read the file or inspect the logs. This pattern adds an HTTP status server alongside the sync loop.

## Architecture

```
media/music-server/syncer/
├── entrypoint.sh         # Starts both status server + sync loop
├── syncer_server.py      # HTTP server with /health, /report, /playlists, /faltantes
├── healthcheck.py        # Script used by Docker healthcheck
├── sync.sh               # Original sync loop (unchanged)
└── summary_report.txt    # Report generated by sync.sh
```

## Pattern: Sidecar HTTP Status

The entrypoint starts two processes:

```bash
# entrypoint.sh
python3 /app/syncer_server.py &    # Status server (background)
exec bash /app/sync.sh             # Sync loop (foreground, blocks)
```

This gives you:
1. **Docker healthcheck** — `curl -f http://localhost:8088/health`
2. **External monitoring** — query status from any tool
3. **Dashboard integration** — music app can show sync progress

## Parsing Pattern

The status server parses the text report without modifying `sync.sh`:

```python
def parse_report() -> dict:
    content = REPORT_FILE.read_text()
    # Regex-extract:
    #   "🎵 PLAYLIST SPOTIFY #1 (...)" → playlist name
    #   "• Requeridas: 150" → total_online
    #   "• Guardadas: 148" → on_disk
    #   "• FALTANTES: 2" → missing
    #   "SINCRONIZACIÓN COMPLETADOS" → status ok
```

This is resilient — if the report format changes, parsing degrades gracefully instead of breaking the sync.

## When to Apply This Pattern

Use this pattern when:
- A container runs a long-running batch job (not a server)
- You need programmatic status access
- You can't modify the main script (it's third-party or complex)
- You want Docker healthchecks without changing the main process

## Pitfalls

1. **Process management** — the entrypoint must use `exec` for the foreground process so Docker signals (SIGTERM) reach it. Background processes with `&` won't receive signals.

2. **Port conflicts** — if the main script also uses HTTP, choose a different port for the status server (8088 vs 4533 for navidrome).

3. **Stale data** — the status server reads a file written by another process. Always check file modification time to detect stale reports.

4. **No authentication** — status servers are typically internal-only. If exposed, add basic auth or bind to localhost only.
