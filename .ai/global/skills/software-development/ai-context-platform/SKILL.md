# AI Context Platform Architecture

Build a platform that prepares context for external AIs. The platform does NOT execute tasks — it provides the "brain" (rules, skills, patterns, memory) so external agents (Claude Code, Trae, etc.) can work with your project standards.

## Core Principle

**The platform does NOT execute tasks. It prepares context for external AIs.**

External AIs are the workers. The platform provides:
- Project-specific masterprompts (how to work in THIS project)
- Global rules and standards (team-wide rules)
- Discovered skills and patterns (learned knowledge)
- Indexed memory (fast context retrieval)

## When to Use

- Building a multi-machine development environment with shared AI context
- Creating a "brain" that any AI agent can consult when working on your project
- Designing context provision that preserves tokens (agents read only what they need)
- Standardizing how AI agents interact with your codebase across machines

## Architecture

### Global Vault (.ai/global/) — The Shared Brain

```
.ai/global/
├── rules/              — Team and project rules
├── skills/             — Discovered tools and skills (YAML)
├── patterns/           — Reusable architecture patterns
├── projects/           — Index of all projects (YAML)
├── index.yaml          — Fast lookup index
└── vault.yaml          — Vault configuration
```

The global vault travels with the project via git. All machines sharing the repo share the same brain.

├── Red y Acceso

├── Multimedia

**Healthchecks are REQUIRED for ALL services.** See `references/healthchecks-all-services.md` for patterns including HTTP, CLI, file-age, sidecar, and API-based checks.

### Local Context (.ai/) — Project-Specific

```
.ai/
├── MASTERPROMPT.md     — Generated template (global + local context)
├── memory.yaml         — Local indexed memory
├── state.yaml          — Current state
├── reports/            — Execution reviews
└── reviews/            — Code reviews
```

### MASTERPROMPT.md — The Bridge

Generated by `ai init`, the masterprompt combines:
- Global rules (from vault)
- Global skills and patterns
- Project-specific structure and instructions

External AIs read this single file to get full context. No repeated explanations needed.

## Workflow

### Installer must be Robust

```bash
bash install.sh
# 1. Pre-flight checks (Python 3.12+, git, curl, sha256sum, venv, Docker, Ollama, VSCode, Trae, Hermes)
# 2. Auto-install missing prerequisites (use correct package manager)
# 3. Create venv, install AIEP
# 4. Configure shell PATH
# 5. Extract bundle (encrypted base config) with shared passphrase
# 6. Prompt for API keys (with optional encryption passphrase)
# 7. Setup .ai/global/ in project
# 8. Schedule periodic sync (cron every 6h)
```

**Critical:** Installer must use `python3.12` if `python3` is too old. Must handle multiple package managers (apt, brew, dnf, pacman, apk, yum). Must clean existing venv if present.

```bash
cd ~/my-project
ai project init [--type web|api|cli|generic] [--context "description"] [--force]
```

**Platform does (in order):**
1. Analyzes the PROJECT — detects language, framework, package manager, dependencies, entry points, tests, Docker, CI
2. Reads `.ai/global/` (rules, skills, patterns)
3. Generates documentation: `ARCHITECTURE.md`, `ROADMAP.md`, `SPEC-001`, `ADR-001`
4. Builds code-graph: indexes components, APIs, models, tests → `.ai/code-graph.yaml`
5. Generates `MASTERPROMPT.md` combining global rules + project analysis + optional user context
6. Creates `.ai/memory.yaml` (with analysis) and `.ai/state.yaml`
7. Populates global vault with default rules (`coding-standards`, `git-workflow`) and patterns (`clean-architecture`, `tdd`)
8. Indexes project in `.ai/global/projects/`
9. Auto-syncs to other machines (via git)

**User can provide context:**
```bash
ai project init --context "This is a payment processing system using Stripe"
```
If no context provided, Hermes analyzes the project automatically.

### 2. Work with External AI

```bash
# Claude Code, Trae, or any AI:
# → Reads MASTERPROMPT.md (complete context)
# → Follows team rules
# → Uses defined skills and patterns
# → Performs the work
```

The AI works with full context without repeated explanations.

### Init with Optional User Context

```bash
ai project init --type api --context "Payment processing system with Stripe"
```

**User provides context:** The `--context` flag lets the user describe their project in their own words. This is incorporated into the MASTERPROMPT.

**No context provided:** Hermes automatically analyzes the project:
- Detects language, framework, package manager
- Scans dependencies, entry points, tests
- Detects Docker, CI, config files
- Builds code-graph of components, APIs, models
- Uses analysis to generate contextualized docs and masterprompt

### Analyzer Must Detect Docker/Infrastructure Projects

```python
# In ProjectAnalyzer._detect_language():
if (root / "docker-compose.yml").exists() or (root / "docker-compose.yaml").exists():
    return "docker"
if (root / "Dockerfile").exists():
    return "docker"

# In _detect_framework():
if language == "docker":
    return "docker-compose"

# In _detect_project_type():
if language == "docker":
    return "infrastructure"
```

**Pitfall:** Without Docker detection, NAS infrastructure projects get classified as "generic" and receive empty/poor documentation.

### Bundle Must Use Efficient Default Model

The bundle's `config.yaml` must use the currently active efficient model, not legacy defaults:

```yaml
# GOOD (current session's model):
model:
  default: meituan/longcat-2.0:free
  provider: nous

# BAD (legacy default, not efficient):
model:
  default: qwen2.5-coder:1.5b
  provider: custom:ollama-launch
```

Generate bundle from a **clean template directory**, never from `~/.hermes/`. Bundle contains ONLY generic base config.

### 3. Sync Discoveries

```bash
ai sync  # or: ai project sync
```

**Platform does:**
1. Reads what the external AI produced
2. Detects new skills, patterns, tools
3. Updates `.ai/global/` with discoveries
4. Auto-syncs to other machines

### 4. On Another Machine

```bash
git pull  # Brings updated .ai/global/
cd ~/my-project
# → External AI reads MASTERPROMPT.md (updated)
# → Has full context without re-configuration
```

## Key Decisions

### Why the platform doesn't execute tasks
- External AIs (Claude, Trae) are more capable workers
- Platform focuses on context preparation (its unique value)
- Saves tokens — agents read only what they need
- Works across machines — same context everywhere
- Agent-agnostic — works with any AI that can read files

### Why MASTERPROMPT.md is generated (not hand-written)
- Combines global + local context automatically
- Updates when global changes (re-run `ai init`)
- Lives in project (travels with git)
- Single source of truth for external AIs

### Why auto-sync via git
- No external service required
- Works offline
- Version controlled
- Standard developer workflow

## Security Patterns

### Credential Encryption
- **Fernet (AES-128-CBC)** for data at rest
- **PBKDF2-HMAC-SHA256** with 600,000 iterations (OWASP 2023)
- Random 32-byte salt per file
- `chmod 0o600` on credential files

### 2FA/TOTP
- RFC 6238 TOTP with ±30 second clock skew tolerance
- Works with Google Authenticator, Authy, 1Password, Bitwarden
- `otpauth://` URI for QR code setup

### File Protection
- `chmod 0o600` on all state/config files
- `fcntl.flock(LOCK_EX)` for race condition prevention
- `yaml.safe_load()` to prevent arbitrary code execution

### Input Validation
- Git URLs validated against remote helper injection (`ext::`, `--upload-pack`)
- Checksum verification for downloaded installers
- `set -euo pipefail` in shell scripts for fail-early

## Installer Requirements

The installer MUST:
1. **Verify prerequisites** before installing anything
2. **Auto-install missing dependencies** (Python, git, curl, etc.)
3. **Handle version mismatches** (e.g., python3 is 3.11, use python3.12)
4. **Support multiple package managers** (apt, brew, dnf, pacman, apk, yum)
5. **Clean up existing venv** if present to avoid conflicts
6. **Configure shell PATH** for the user

### Auto-Sync Pattern

Use `ctx.call_on_close()` in Typer for reliable post-command sync:

```python
@app.callback(invoke_without_command=True)
def main_callback(ctx: typer.Context) -> None:
    if ctx.invoked_subcommand:
        _auto_sync_before_command()
        ctx.call_on_close(_auto_sync_after_command)  # Always runs, even on error
```

## Multi-Agent Bridge Patterns (NEW 2026-08-20)

When AIEP serves as central brain for multiple IAs (Hermes, Claude, Codex, Aider), implement these bridges:

### Hermes Bridge (`aiep/hermes_bridge/`)
Imports Hermes skills + memory into AIEP vault:
```python
from aiep.hermes_bridge.core import HermesBridge
bridge = HermesBridge(project_root="/path/to/project")
bridge.import_skills()   # 89 skills → .ai/global/skills/
bridge.sync_memory()     # Hermes memory → .ai/global/memory/
bridge.export_context()  # AIEP context → Hermes-readable YAML
```

### IA Bridge (`aiep/ia_bridge.py`)
Detects installed IAs and propagates rules bidirectionally:
```python
from aiep.ia_bridge import IARegistry, RuleSyncService
registry = IARegistry.detect_installed()  # {"hermes", "claude", "aider"}
service = RuleSyncService()
service.add_rule({"text": "Always update docs"}, source="user")  # → all IAs
service.sync_all()  # propagate all rules to all IAs
```

### Auto-Sync Middleware Enhancement
The post-command sync now includes 4 additional steps:
1. `_sync_hermes_skills()` — Import Hermes skills to vault
2. `_sync_hermes_memory()` — Sync Hermes memory
3. `_sync_ia_rules()` — Propagate rules to all IAs
4. `_update_documentation()` — Update MASTERPROMPT + ROADMAP with active rules

**Key insight**: When ANY IA says "always do X", that rule propagates to ALL other IAs via AIEP.

## Pitfalls

- **Platform executing tasks** — it shouldn't, that's external AI's job
- **Manual masterprompt writing** — generate it from global context
- **Forgetting auto-sync** — use `call_on_close()` not just sequential calls
- **Not verifying prerequisites** — install.sh must check AND install
- **Storing credentials plaintext** — always encrypt with Fernet
- **Race conditions on shared files** — use file locking
- **Blocking the user** — sync must be silent and non-blocking
- **External service dependency** — use git for sync, no server required
- **Init creates only empty structure** — `ai init` must analyze the PROJECT (stack, files, deps), generate real documentation (architecture, specs, roadmap), create code-graph, run security analysis, and populate global vault with rules/skills/patterns. Empty directories are NOT a working init.
- **MASTERPROMPT.md stubs are common** — `ai init` often generates a template with placeholder text (`_Descripción..._`, `_Sin memoria aún_`), broken internal references, and AIEP-specific commands that don't apply. Always complete the stub with real project data using the workflow in `references/masterprompt-completion-workflow.md`.
- **Copying host config to bundle** — bundle must contain only GENERIC base config, never real credentials from the host machine. Generate bundle from a clean template directory, never from `~/.hermes/`.
- **Using inefficient default models** — bundle should use the currently active efficient model (e.g., meituan/longcat-2.0:free), not legacy defaults like qwen2.5-coder:1.5b.
- **Git repo leaking secrets** — always audit with `git ls-files | grep -E "(\.env|auth|token)"` and `grep -r "sk-\|ghp_\|AKIA" .` before committing.
- **Python version mismatch** — if `python3` is too old (<3.12), installer must detect and use `python3.12` explicitly.
- **Shell injection in install scripts** — validate URLs against git remote helper injection (`ext::`, `--upload-pack`).
- **Install.sh asking for passphrase when already configured** — if `config.yaml` already exists, skip bundle extraction entirely. Don't ask the user for a passphrase they may have forgotten.
- **uv venv "already exists" error** — use `uv venv --clear` or fall back to `rm -rf` then recreate.
- **Large model timeout** — qwen3.6 36B causes connection resets on some setups. Prefer gemma4:12b or llama3.2:latest for AI-powered doc generation, keep qwen2.5-coder:1.5b as fast fallback.
- **Thread-based background AI fails** — daemon threads die when the main process exits. Use `subprocess.Popen` with `start_new_session=True` for truly background AI calls, or accept blocking with timeout.
- **Sync must target AIEP repo, not local** — auto-sync must push/pull project context to/from the AIEP platform repo (`projects/<name>/`), not just the local `.ai/global/` directory. See references/auto-sync-architecture.md.
- **Rules in git** — Rules propagated to IAs may be committed to git. Never store secrets in rules; use AIEP vault secrets for credentials.
- **Hermes skills not visible to VS Code agent** — VS Code in agent mode uses AIEP's internal catalog, not Hermes skills. The Hermes Bridge syncs skills to AIEP vault, but VS Code may need a refresh to see them.
- **Docker projects classified as "generic"** — analyzer must detect `docker-compose.yml`/`Dockerfile` as language "docker", framework "docker-compose", type "infrastructure". Without this, Docker NAS infrastructure projects get generic treatment and poor documentation.
- **NAS ARM64 model compatibility** — when deploying to NAS (ARM64), verify model availability for the architecture. Not all models have ARM builds.
- **Init running on wrong project** — when `ai project init` is invoked from a subdirectory of the AIEP platform repo itself, it can accidentally run on the platform instead of the target. Always verify the target directory and working directory before running init.
- **Bundle must never copy host config** — the bundle.aiep must contain ONLY generic base config. Never generate it from `~/.hermes/` or copy real credentials. Always use a clean template directory.
- **Inefficient default models** — the bundle should use the currently active efficient model (e.g., meituan/longcat-2.0:free), not legacy defaults like qwen2.5-coder:1.5b.
- **Large local models cause OOM** — GLM-5.2 (744B) cannot run on 15GB RAM even with mmap. Don't promise local deployment of massive models without verifying hardware. Use API fallback for large models.
- **Night job for heavy analysis** — intensive analysis (prospect/client history, recommendations) should run as a scheduled night job, not interactively. Store results in SQLite, notify via Telegram for high-priority issues. See references/minegocio-analyzer-night-job.md.
- **Firebase Admin SDK in NAS** — NAS services reading MiNegocio data need Firebase Admin SDK with service account. Store service account JSON in `/volume1/Docker/secrets/` mounted read-only, never in repo.
- **React Router route duplication** — when adding new routes in `App.tsx`, ensure the path doesn't collide with existing routes (e.g., `/customers` vs `/customers/:id`). Use `Customers` list for collection and `CustomerDetails` for single item.
